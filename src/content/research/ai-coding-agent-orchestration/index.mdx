## 核心发现

<KeyFinding level="high">
  AI Coding Agent 编排层正在从纯模型驱动的 ReAct 循环向「混合编排」范式收敛。关键分野不在于是否使用 LLM，而在于将**编排关注点**（循环、分支、屏障）与**推理关注点**（上下文理解、模式匹配）分离的程度。Claude Code Dynamic Workflows 是这一趋势的标志性实现。
</KeyFinding>

<KeyFinding level="high">
  上下文漂移是所有 AI coding agent 的根本瓶颈。EvoClaw 基准测试量化了这一点：代理在孤立任务上表现超 80%，但在连续演化场景中骤降至 38% 以下。编排层分离本质上是在架构层面回应这个问题——把控制流移出上下文窗口，让 LLM 只负责它擅长的推理。
</KeyFinding>

<KeyFinding level="medium">
  并发能力是编排层设计的试金石。Claude Code 通过模型生成 JS 脚本实现数十到数百个子代理扇出；OpenAI Codex 采用 manager-worker 模式实现并发线程；学术方案（SPOQ）证明 DAG 拓扑排序可达 14.3 倍理论加速。但硬件受限时（2 GPU 槽位），加速回落至约 1.4 倍——并发的收益受物理约束封顶。
</KeyFinding>

### Claude Code：混合编排的典型实现

<VerdictCard
  claim="Claude Code 底层是 ReAct 模式 while 循环（1.6% AI 决策逻辑 + 98.4% 确定性基础设施），上层通过 Dynamic Workflows 让模型生成 JavaScript 编排脚本，将控制流从上下文窗口迁移到确定性代码中执行"
  verdict="confirmed"
  votes="5 条合并声明，均为 3-0 通过"
/>

Claude Code 的架构揭示了一个反直觉的事实：**一个 AI coding agent 中真正由 AI 驱动的部分极其精简**。VILA-Lab 的源码逆向分析（基于 2026 年 3 月泄露的 v2.1.88）确认，核心代码中仅 1.6% 是 AI 决策逻辑，其余 98.4% 是确定性的基础设施——工具路由、权限检查、上下文管理、错误恢复等。

2026 年 5 月 28 日发布的 Dynamic Workflows（v2.1.154）将这一分离推到了极致：

1. **模型生成编排脚本** — LLM 根据任务需求编写一段 JavaScript，定义循环、分支、屏障（barrier）等控制流
2. **隔离沙箱执行** — 脚本在独立运行时环境中执行，不占用对话上下文窗口
3. **子代理并行扇出** — 脚本通过 `agent()`/`parallel()`/`pipeline()` 原语派发数十到数百个子代理
4. **中间状态存于脚本变量** — 不回流到 LLM 上下文，只有最终结果返回

这是「模型生成、确定性执行」的混合范式：LLM 负责理解任务和设计编排策略（推理关注点），执行引擎负责可靠地运行这个策略（编排关注点）。

### OpenAI Codex CLI：迭代循环 + 多代理

<VerdictCard
  claim="Codex CLI 采用迭代式代理循环，支持 manager-worker 多代理编排模式，管理者分解任务并派发给并行 worker，每个 worker 拥有独立上下文窗口"
  verdict="confirmed"
  votes="2 条合并声明，3-0 和 2-1"
/>

Codex 的架构相对传统但有效：

- **核心是单代理循环**：每轮 Turn 由「推理 + 工具调用」组成，循环直到任务完成
- **多代理为附加能力**：通过 `spawn_agent`/`wait_agent` 工具实现 manager-worker 派发
- **增量上下文传递**：使用 `previous_response_id` 而非重放完整历史，配合 auto-compaction 机制

与 Claude Code 的关键区别：Codex 的编排逻辑仍在代理循环内部（LLM 上下文中），而非迁移到外部确定性运行时。这意味着编排决策本身消耗上下文窗口预算。

### 学术视角：SPOQ 的 DAG 调度

<VerdictCard
  claim="SPOQ 通过对依赖 DAG 做拓扑排序预计算并行波次，在无界基准上实现 14.3 倍加速，硬件受限时稳定在约 1.4 倍"
  verdict="confirmed"
  votes="3 条合并声明，均为 3-0 通过"
/>

[SPOQ](https://arxiv.org/html/2606.03115v1)（2026 年 6 月 arxiv 预印本）明确将编排与执行视为可分离关注点：

- 对标 [ChatDev](https://github.com/OpenBMB/ChatDev) 的顺序角色扮演和 [MetaGPT](https://github.com/geekan/MetaGPT) 的消息传递
- 提出确定性 DAG 调度 + LLM 任务执行的分离架构
- 临界路径比 1.03-1.11（近理论最优）
- **Human-as-an-Agent 模型**：将人类审查建模为 DAG 中的一个节点，残余缺陷从 0.47 降至 0.03/任务

<Callout type="warning" title="数据局限">
  SPOQ 的 14.3 倍加速来自合成 sleep 基准（DAG-20-D1 配置），非真实代码库任务。硬件受限场景（2 GPU 槽位）实际加速仅约 1.4 倍。论文尚未经同行评审。
</Callout>

### 上下文管理策略

<VerdictCard
  claim="Claude Code 通过双路径工具执行（StreamingToolExecutor + runTools）实现并发，配合 5 层渐进式上下文压缩管线和纯文件式记忆系统管理状态"
  verdict="partial"
  votes="2 条合并声明，2-1 和 3-0"
/>

Claude Code 的上下文管理是一个 5 层渐进式压缩管线（按成本递增触发）：

1. **Budget Reduction** — 裁剪低价值 token（工具输出摘要等）
2. **Snip** — 移除中间对话轮次的详细内容
3. **Microcompact** — 超短摘要替换旧消息
4. **Context Collapse** — 折叠整段对话为关键结论
5. **Auto-Compact** — 最后手段，全面重写上下文

记忆系统完全基于文件（CLAUDE.md），无向量数据库，可版本控制和人工审查。这是一个有意的设计选择：**显式优于隐式，可审计优于魔法**。

<Callout type="insight" title="洞察">
  Dynamic Workflows 的核心价值不仅是并发，更是**上下文压力的根本性缓解**——中间结果存在 JavaScript 变量中而非对话上下文中，从 O(n × output_size) 降为 O(final_result)。这解释了为何它能处理单上下文窗口根本无法容纳的任务。
</Callout>

## 三、上下文漂移：共同的敌人

<VerdictCard
  claim="上下文漂移是所有 AI coding agent 的核心瓶颈：EvoClaw 基准测试显示代理在孤立任务上表现超过 80%，但在连续演化设定中骤降至最多 38%"
  verdict="confirmed"
  votes="3-0"
/>

[EvoClaw](https://arxiv.org/abs/2603.13428)（2026 年 3 月）测试了 12 个前沿模型和 4 个代理框架，量化了一个核心现象：

> 当代码库在多轮任务间持续演化，代理对系统级不变量的理解逐渐崩塌。

这不是简单的「上下文太长」问题——即使窗口足够大，**信息的一致性维护**才是瓶颈。具体表现：

- 孤立任务（给定完整上下文）：各模型表现 80%+
- 连续演化（需要追踪跨任务的状态变化）：骤降至最多 38%
- 性能崩塌点与任务序列长度强相关，而非绝对上下文长度

这解释了为何 Claude Code 和 SPOQ 都不约而同地将编排逻辑移出上下文窗口——这不是优化，而是**必要的架构约束**。

## 五、被驳回的流行说法

以下声明在对抗验证中被驳回，值得特别关注——它们代表了当前围绕这些工具的常见误解：

<VerdictCard
  claim="到 2026 年 6 月，Claude Code、Cursor、Codex 和 Antigravity 已经收敛到同一种代理编码蓝图架构"
  verdict="rejected"
  votes="0-3"
/>

现实是这些工具的编排架构差异极大。Claude Code 走向确定性脚本编排，Codex 保持传统代理循环加多代理扩展，Cursor 和 Windsurf 的内部实现不透明。「收敛」的说法可能来自表面功能相似性（都能写代码、都能用工具），而非架构层面的真正趋同。

<VerdictCard
  claim="Dynamic Workflows 支持每次运行最多 1,000 个并行子代理"
  verdict="rejected"
  votes="0-3"
/>

多个三方来源声称 1,000 并行子代理，但对抗验证发现这个数字缺乏 Anthropic 官方确认，更可能是并发槽位上限（min(16, cpu cores - 2)）与累计代理数上限的混淆。实际并行度受硬件约束远低于此。

<VerdictCard
  claim="Claude Code 强调审批密集型工作流，是对比工具中最注重 human-in-the-loop 的"
  verdict="rejected"
  votes="0-3"
/>

Claude Code 的权限模式是一个可调光谱（从 plan mode 到 bypass），而非固定的「审批密集型」。用户可以根据信任度动态调整，这与「最注重 HITL」的定位不符。

## 七、开放问题

1. **Cursor 和 Windsurf 的黑箱**：Background Agent 和 Cascades/Flows 的编排架构细节完全不透明，无法进行可靠的技术对比。这是市场策略还是尚未成熟？

2. **Dynamic Workflows 的生产验证**：仍处于 research preview 阶段（仅 Max/Team/Enterprise 可用），缺乏大型代码库（>100K LOC）上的可靠用户报告。

3. **上下文窗口扩大是否让编排层过时**：当窗口持续扩大（1M+ tokens），上下文漂移问题会自然缓解，还是编排层分离仍然是必要的架构选择？EvoClaw 的数据暗示答案是后者——问题在于信息一致性维护，而非绝对容量。

4. **任务类型 × 编排模式的 ROI**：确定性 DAG、模型生成脚本、纯 ReAct 循环对不同任务类型（重构、bug 修复、绿地开发）的效率差异缺乏定量对比。
