## 核心发现

<KeyFinding level="high">
  Spec-driven 开发已成为 AI 编程的主流范式，7 个主要框架在不到一年内累计 500K+ GitHub stars。但没有任何一个框架经过独立的经验性评估——整个领域建立在理论论证和用户证言之上，而非受控实验。
</KeyFinding>

<KeyFinding level="high">
  知识积累能力是框架间最大的分化点。Compound Engineering 的"解决方案文档化→检索→计划"闭环和 Spec Kitty 的"回顾→治理变更提案"机制是目前仅有的两个真正的正反馈循环。其余框架的知识积累更多是被动的文件堆积。
</KeyFinding>

<KeyFinding level="medium">
  流行度与流程完备性正交。Spec-Flow（85 stars）在学术评估中得分 11/12，远超 GSD（64K stars，4/12）和 Spec Kit（109K stars，8/12）。开发者的选择被营销、生态整合和上手摩擦驱动，而非流程质量。
</KeyFinding>

## 二、各框架深度分析

### 2.1 Superpowers — 最大社区，LLM 行为工程先锋

- **仓库**：[obra/superpowers](https://github.com/obra/superpowers) | **219K stars** | MIT
- **作者**：Jesse Vincent（Anthropic 工程师）
- **架构**：纯 Markdown，零运行时依赖，通过 LLM 上下文注入生效
- **核心创新**：**反合理化工程**——每个技能都包含"合理化借口表"，预见并堵住 LLM 的 12 种逃避策略

**七阶段工作流**：Brainstorm → Git Worktree → Plan → SDD（子代理驱动开发）→ TDD → Code Review → Finish

<Callout type="insight" title="非显而易见的洞察">
  CSO（Claude Search Optimization）是一个隐藏的关键创新：技能的 description 字段被刻意设计为只描述触发条件而不描述工作流。实测发现当 description 概括了流程时，LLM 直接按 description 做了就跳过了完整流程。这本质上是对 LLM"偷懒"行为的逆向工程。
</Callout>

### 2.2 GitHub Spec Kit — 官方背景，模板即约束

- **仓库**：[github/spec-kit](https://github.com/github/spec-kit) | **109K stars** | MIT

**工作流**：Constitution → Specify → Clarify → Plan → Analyze → Tasks → Implement → Checklist → Tasks-to-Issues

### 2.3 GSD (Get Shit Done) — 上下文工程专家

- **仓库**：[open-gsd/gsd-core](https://github.com/open-gsd/gsd-core) | **64K stars** | MIT
- **架构**：文件驱动状态机，.planning/ 目录存储所有状态，纯 Markdown/JSON
- **核心创新**：**上下文工程**——将"agent 应该读什么、按什么顺序、在什么框架下"作为一等工程学科

**工作流**：Discuss → UI Design → Plan（研究→计划→计划审查）→ Execute（并行波次）→ Verify → Ship

### 2.4 OpenSpec — 最轻量，Brownfield 友好

- **仓库**：[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) | **53K stars** | MIT
- **架构**：TypeScript CLI（npm 包），openspec/ 目录存储规范和变更
- **核心创新**：**Delta 规范模型**——变更表达为 ADDED/MODIFIED/REMOVED 相对于现有规范，而非重写

**工作流**：Explore → Propose → Create Artifacts（DAG 驱动）→ Implement → Verify → Sync → Archive

### 2.5 BMAD Method — 流程最深，角色分离最强

- **仓库**：[bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | **49K stars** | MIT
- **架构**：微文件架构，每个步骤独立文件避免 LLM 注意力稀释
- **核心创新**：**角色分离** + **SPEC.md 变更合约**（独占写入权，架构级约束而非流程级建议）

**角色管线**：Analyst (Mary) → PM (John) → UX Designer (Sally) → Architect (Winston) → IR Gate → Developer (Amelia) → Tech Writer (Paige)

### 2.6 Compound Engineering — 知识复利最强

- **仓库**：[EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin) | **20K stars** | MIT
- **架构**：50+ 专用子代理，docs/solutions/ 结构化知识库 + CONCEPTS.md 词汇表
- **核心创新**：**知识复利闭环**——ce-compound 自动文档化 → learnings-researcher 自动检索 → ce-plan 自动整合

**知识循环核心**：每次完成工作 → ce-compound 并行调度 3 个子代理提取解决方案 → 写入 docs/solutions/（YAML frontmatter + Markdown）→ 下次 ce-plan 时 learnings-researcher 自动 grep 搜索历史方案 → 避免重复造轮子

## 六、结构性权衡：可移植性 vs 流程深度

<KeyFinding level="high">
  可移植性和流程深度存在根本性张力。轻便的框架（OpenSpec、Spec Kit）支持 25-33 个 agent 但无法深度整合执行和验证；深流程框架（BMAD、Spec Kitty）提供强治理但耦合特定 agent 能力。没有框架同时解决了两者。
</KeyFinding>

## 八、领域趋势判断

1. **上下文工程正在成为独立学科**：GSD 将"agent 该读什么、按什么顺序、在什么框架下"作为一等公民。Compound Engineering 用 grep-first 检索结构化 frontmatter。这种认识——LLM 输出质量由输入上下文质量主导，而非模型本身——正在催生独立于 prompt engineering 的新学科。

2. **规范只是入场券，验证是前沿**：所有框架在 specification 维度得分 1-2，这已是共识。真正的分化在于能否验证实现与规范的一致性——目前没有框架能程序化地做到这一点，所有验证都依赖 LLM 判断，形成循环依赖。

3. **AI 开发工具的供应链安全缺失**：社区扩展（schema、模板、预设）无签名、无权限范围、无验证机制。这是等待发生的"npm left-pad 事件"。

4. **18 个月内大概率整合为 2-3 个存活者**：7 个高度重叠的框架不可持续。胜出者将是首先实现经验性验证、解决可移植性-深度权衡、并建立可持续生态的框架。

5. **零经验性验证**：整个 spec-driven 开发范式建立在理论论证和用户证言之上。首个发布严格 A/B 测试结果的团队将对领域方向产生超比例影响力。
