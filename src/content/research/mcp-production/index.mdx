## 核心发现

<KeyFinding level="high">
  MCP 的主要故障面在**能力执行和 Schema 层**，而非传输或协议层。473 个仓库中 837 个故障线程的实证分析表明，工具故障(23.2%)、数据与 Schema 故障(17.6%)、状态与配置故障(17.1%) 三类占总量的 57.8%。这意味着生产环境最大的风险不是「连不上」，而是「连上了但行为不对」。
</KeyFinding>

<KeyFinding level="high">
  MCP 生态的安全基础远未达到生产标准。5,205 个开源 server 中 88% 需要凭证，但 53% 依赖静态 API Key/PAT，仅 8.5% 实现 OAuth。学术扫描发现 106 个零日漏洞和 67 个 CVE。协议规范本身声明无法在协议层面强制执行安全——安全完全依赖各 server 实现者自律。
</KeyFinding>

<KeyFinding level="medium">
  2026-07-28 新规范 RC 标志着 MCP 从「有状态连接」向「无状态 HTTP」的根本性转型。去除协议级会话和 initialize 握手后，核心层变为无状态，这降低了集成门槛但进一步弱化了服务端对客户端的控制能力——版本管理和工具完整性验证变得更加困难。
</KeyFinding>

<Callout type="insight" title="非直觉洞察">
  传输和协议层故障占比最低，反而最不危险——因为它们产生明确的错误信号。真正危险的是 Schema 和工具层的故障：它们通过所有表面检查，却在运行时产生错误行为。这与分布式系统领域的经典教训一致：**最危险的故障不是系统崩溃，而是系统在错误状态下继续运行**。
</Callout>

### 灰色故障：MCP 的隐形杀手

<VerdictCard
  claim="MCP 存在灰色故障模式：server 返回格式正确的 JSON-RPC 成功响应，但实际行为与预期不符。配置参数被接受但运行时不强制执行。这类故障通过所有常规健康检查，只能通过行为级端到端验证发现"
  verdict="confirmed"
  votes="3-0"
>
  类比分布式系统中的 gray failure 概念（[Huang et al. 2017 HotOS](https://www.usenix.org/conference/hotos17/program/presentation/huang)）。已确认的实例包括：smart-tree 工具结果未传播、[apache/apisix](https://github.com/apache/apisix) 的 include_resp_body 被静默覆盖、jupyter-mcp-server 返回合法 JSON-RPC 但内容偏差。
</VerdictCard>

灰色故障在 MCP 生态中尤其危险，因为 LLM 客户端通常只检查 JSON-RPC 响应格式是否正确，不具备验证语义正确性的能力。一个典型的攻击/故障链：

1. MCP server 接受请求并返回 `result: {...}` 格式正确的响应
2. LLM 客户端将其视为成功，继续基于该结果推理
3. 推理基于错误数据，产生错误决策
4. 用户看到的最终输出看起来合理，但建立在错误基础上

<Callout type="warning" title="防御建议">
  生产环境中必须实施行为级端到端验证——不仅检查响应格式，还要抽样验证响应内容的语义正确性。这需要在 MCP 客户端层或中间代理层实现，因为协议本身不提供此能力。
</Callout>

### 恶意 Server 攻击面

MCP 协议设计中存在一个根本性安全缺陷：**工具描述在初始批准后可被 server 动态修改**。这意味着：

1. 用户审批了一个看起来无害的工具描述
2. Server 在后续会话中修改工具描述，注入恶意指令
3. LLM 按照新的（恶意）描述执行工具调用
4. 用户的初始审批已无效，但系统不会重新请求授权

这不是理论攻击——[Equixly 的分析](https://equixly.com)确认了此攻击路径的可行性。

<Callout type="insight" title="去状态化的双刃剑">
  去除协议级会话使 MCP server 更容易部署在无状态基础设施上（Lambda、Cloud Run 等），显著降低了生产化门槛。但这同时意味着 server 失去了跨请求追踪客户端身份的原生能力——认证、速率限制、审计日志等全部需要在应用层重新实现。**便利性和安全控制力的此消彼长**，是这次规范变更最值得关注的张力。
</Callout>

### Roots/Sampling/Logging 废弃的影响

三项功能废弃虽给出了 12 个月过渡期，但实际影响可能更深远：

- **Roots**：用于限定 server 可访问的文件系统路径。废弃后，路径限制需在 server 实现层自行处理
- **Sampling**：允许 server 请求 LLM 补全。废弃后，server 无法再通过协议层借用客户端的 LLM 能力
- **Logging**：标准化日志格式。废弃后，日志格式碎片化

<Callout type="insight" title="抽象层级错位的教训">
  AWS 的警告揭示了一个常见的架构错误：将 MCP 用于 agent 间通信。MCP 设计的核心抽象是「工具调用」——请求/响应式的能力接入。Agent 间通信需要的是任务委派、进度通知、能力发现等完全不同的交互模式。用错误的抽象解决问题，不会导致编译错误，只会导致更微妙的架构腐化。

## 五、版本管理：被忽视的定时炸弹

<VerdictCard
  claim="MCP 工具 Schema 的破坏性变更会静默腐蚀 agent 行为，且无编译期或部署期检测机制。MCP 协议不提供工具描述的密码学签名或完整性验证。2026-07-28 RC 去状态化后进一步弱化"
  verdict="confirmed"
  votes="3-0"
>
  [AWS 技术博客](https://aws.amazon.com)确认。这是 MCP 生产化面临的最隐蔽风险之一。
</VerdictCard>

版本管理问题的严重性在于其**静默性**。考虑以下场景：

1. **Day 1**：Agent 学习了 `search_database` 工具，参数为 `{query: string, limit: number}`
2. **Day 30**：Server 更新，`limit` 参数改为 `max_results`，旧参数被静默忽略
3. **Day 31**：Agent 仍发送 `limit: 10`，server 接受请求但使用默认值 `max_results: 1000`
4. **结果**：查询返回 100 倍的数据量，agent 处理超时或产生错误结论

这不是假设场景——它是 MCP 灰色故障的一个子类。没有编译器、没有类型检查、没有部署检查会捕获这个问题。在传统 API 管理中，这类问题通过 API 版本号、OpenAPI 规范的 breaking change 检测、合约测试等机制缓解。MCP 生态目前没有这些。

<Callout type="warning" title="生产环境建议">
  在 MCP 客户端层实现工具 Schema 快照和差异检测：定期拉取工具列表并与基线对比，Schema 变更触发告警和人工审查。这是在协议层缺乏版本管理能力时的必要补偿措施。
</Callout>

## 七、被驳回的声明

## 九、开放问题

1. **MCP 工具调用的 token 消耗精确基准**：有报告称 [Firecrawl](https://github.com/mendableai/firecrawl) MCP server 单次调用消耗 32K-82K token，而 CLI 替代方案仅约 200 token。但该对比未通过对抗验证，实际数据可能因场景而异。生产环境中 token 成本是否会成为 MCP 的隐性瓶颈？

2. **去会话化后的迁移成本**：现有基于 Mcp-Session-Id 维护状态的实现（特别是 Sampling 功能的使用者）需要多大的迁移工作量？12 个月过渡期是否充分？

3. **20,000+ server 中生产可用的比例**：Astrix 审计的 5,205 个 server 中，安全态势令人担忧。考虑到审计覆盖率仅约 25%，剩余 75% 的情况可能更糟。在企业安全标准下，实际可用的 server 比例可能远低于预期。

4. **MCP + A2A + AG-UI 之外的替代方案**：当前三层模型是否是最终答案？ACP（IBM）的定位与 A2A 重叠但侧重不同，是否会形成有意义的替代？AG-UI 是否会被更通用的流式协议取代？

5. **灰色故障的系统性防御**：当前除人工审查外，没有自动化手段检测 MCP 灰色故障。是否可能在协议层或中间件层引入行为合约（类似 Pact 合约测试）自动检测？

## 研究局限

<Callout type="warning" title="需要注意的局限">
  1. arXiv 2606.05339 为预印本，55 人开发者验证样本有限，故障分类法尚需更大规模验证。
  2. Astrix Security 的审计方法为 LLM 辅助 README 分析（非深度代码审计），约 30% 仓库被排除。Astrix 已被 Cisco 收购（~$400M），数据解读需考虑商业动机。
  3. 2026-07-28 新规范为 Release Candidate，正式版可能有变更。
  4. AG-UI 的三层协议栈定位主要来源于 CopilotKit 的自我营销叙事，虽已获生态采纳但需保持警惕。
  5. token 消耗对比（Firecrawl 32K-82K vs CLI 200 token）未通过对抗验证，不应作为决策依据。
  6. 安全漏洞数据（106 个零日、67 个 CVE）来自自动化扫描工具，可能包含误报。
</Callout>
