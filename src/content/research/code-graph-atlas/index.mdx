## 核心发现

<KeyFinding level="high">
  代码图谱正经历**从编译器内部数据结构到 AI 编码基础设施的范式转型**。最关键的趋势是代码图谱通过 MCP 协议向 AI Agent 暴露结构化上下文——五类多跳推理查询（影响分析、依赖链追踪、接口实现查找、数据流追踪、架构模式识别）对向量检索结构性不可达，图遍历是不可替代的补充。
</KeyFinding>

<KeyFinding level="high">
  **90% 的代码图谱场景不需要专用图数据库。** [CodeGraph](https://github.com/nicobailey/CodeGraph)（44K+ stars）用 SQLite WAL + FTS5 + 递归 CTE 实现完整代码图谱，支持 33 语言。SQLite 递归 CTE 适合 3-5 跳遍历，只有 6+ 跳深度遍历、图算法（PageRank/社区检测）或十万级以上节点的模式匹配才需要 [Neo4j](https://neo4j.com) 或 [Memgraph](https://memgraph.com)。
</KeyFinding>

<KeyFinding level="medium">
  **GitHub 先后归档 [Semantic](https://github.com/github/semantic)（Haskell）和 [Stack Graphs](https://github.com/github/stack-graphs)（Rust）**，证明自建完整语义分析框架的维护成本在工业界不可持续。行业最终倾向于组合现有工具（[Tree-sitter](https://tree-sitter.github.io/tree-sitter/) + SCIP indexers）而非从头构建。
</KeyFinding>

### CPG：最终的统一抽象

CPG（Code Property Graph，代码属性图）由 [Yamaguchi 等人于 2014 年提出](https://ieeexplore.ieee.org/document/6956589)，通过让 CFG 节点继承 AST 节点，在同一节点集上叠加 AST 边、CFG 边、CDG 边、REACHING_DEF 边，实现多视图融合。[Joern](https://joern.io) CPG 规范 1.1 定义了 15 个层、40+ 种节点类型，是安全分析和 AI 上下文检索的核心抽象。

### SSA：数据流分析的分水岭

SSA（Static Single Assignment）形式将 def-use 链从多对多简化为一对一，使几乎所有经典优化降级为图遍历。CFG 上的支配边界用于放置 Phi 函数，是现代编译器（LLVM、GCC、V8 TurboFan）的基础。

<Callout type="insight" title="非直觉洞察">
  **动态语言是所有表示的阿喀琉斯之踵**——eval、动态分派、反射使静态分析精度本质受限。调用图构建算法沿 CHA→RTA→VTA→指针分析的帕累托前沿递进，精度与开销呈对数关系，但动态语言打破了这一前沿。务实的做法是接受 80% 精度的语法级调用图，配合运行时 profiling 或 LLM 语义推断修正。
</Callout>

工具链存在**「精度-通用性-性能」不可能三角**。

### Tree-sitter：语法层事实标准

[Tree-sitter](https://tree-sitter.github.io/tree-sitter/) 基于 GLR 变体（默认 LR(1) + 冲突时局部切换 GLR），增量解析基于 Tim Wagner 的研究，复杂度 O(变化大小)。当前 v0.26.9，被 Neovim/Zed/Helix/VS Code 1.123 采用。

<Callout type="warning" title="常见集成陷阱">

### SCIP：取代 LSIF 的离线索引标准

[SCIP](https://sourcegraph.com/docs/code-intelligence/scip)（Sourcegraph Code Intelligence Protocol）基于 Protobuf + 人类可读字符串 ID，相比 LSIF 体积缩小 4-8 倍、处理速度提升 3 倍。当前覆盖 Java/Scala/Kotlin/TypeScript/Rust/C++/Python 等 13 种语言。

### 代码图 Schema 事实标准

Schema 设计已在各开源项目中高度收敛，新项目应直接复用而非重新设计：

**节点类型（8-10 个）：** File（path/language/hash）、Module（name/isExternal）、Class（name/visibility/isAbstract）、Function（name/signature/isAsync）、Method（isStatic/isConstructor）、Variable（type/isConst/scope）、Import（source/specifiers）、Type（kind: interface/enum/type_alias），按需加 Route（API 端点）和 Component（UI 组件）。

**边类型（核心 7 个）：** CONTAINS / CALLS / IMPORTS / EXTENDS / IMPLEMENTS / REFERENCES / DEPENDS_ON。边可携带属性（CALLS 边附加 line 和 isDynamic，IMPORTS 边附加 isDefault 和 alias）。

<Callout type="tip" title="增量更新最佳实践">
  文件级原子替换（同一事务中删旧建新）+ content hash 校验（避免假阳性）+ unresolved_refs 表诚实记录无法解析的引用。开发时实时增量更新 + CI/CD 全量重建 = 兼顾体验和正确性。版本化存储需求通常被高估——git commit hash 打标签+按需重建比时态图数据库简单得多。
</Callout>

<Callout type="warning" title="性能杀手：超级节点">
  Object 基类、utils 模块、index.ts 桶文件等超级节点是所有图数据库的性能杀手。应在 schema 设计层面标记为虚拟聚合节点，查询时限制展开深度。所有参与 MATCH/MERGE 的属性必须建索引，可变长度路径查询务必设上限（`*1..10` 而非 `*1..`）。
</Callout>

<Callout type="insight" title="非直觉洞察">
  大多数算法的核心困难不在图算法本身，而在**调用图构建精度**——虚调用、反射、动态分派使调用图存在 over-approximation（误报）和 under-approximation（漏报）的根本权衡。死代码检测看似简单（入度为零的节点），实际面临反射调用、依赖注入、配置驱动路由等动态特性的严重挑战。

## 六、深度领域：Tree-sitter + 图数据库

### Tree-sitter 深入分析

#### GLR 变体：按需分叉

Tree-sitter 的解析策略是精心设计的工程折中——默认 LR(1) 保持线性性能，仅在 `grammar.js` 的 `conflicts` 声明触发的歧义点局部切换 GLR 分叉。每条分叉路径独立维护解析栈，通过 `prec.dynamic` 累计动态优先级选择最优解析。这种「按需 GLR」策略使其在 99% 的输入位置保持 O(n) 性能。

#### 增量解析机制

基于 Tim Wagner 的研究，分两步执行：

1. **`ts_tree_edit`**：仅调整坐标（字节偏移+行列位置），不做任何重解析
2. **`ts_parser_parse_string`**：传入编辑后的旧树，解析器内部共享未受影响的子树结构

实现 O(变化大小) 的增量更新——对万行文件的单字符编辑，重解析成本与文件大小无关。

#### Grammar DSL 三层优先级

- **词法优先级**：`prec` 在 `token()` 内，决定选哪个 token
- **解析优先级**：`prec` 在外部，决定哪条规则解释 token 序列
- **动态优先级**：`prec.dynamic`，GLR 分叉后的运行时选择

外部扫描器（`externals`）处理正则无法描述的 token（如 Python 缩进、Bash heredoc），需实现 create/destroy/serialize/deserialize/scan 五个函数。

#### 查询系统

S-expression 查询语法支持：字段限定（`field:`）、通配符（`_`）、量词（`+`/`*`/`?`）、备选（`[]`）、锚点（`.`）、否定字段（`!field`）和谓词（`#eq?`/`#match?`/`#any-of?`）。推荐使用查询模式匹配而非 TreeCursor 遍历来提取实体——声明式、易维护且可跨语言复用。

### 端到端集成方案

从代码到可查询图的六步流水线：

1. **解析**：Tree-sitter 解析源文件得到 CST，通过 `_named_` 系列 API 过滤匿名节点
2. **实体提取**：S-expression 查询提取五类关键模式（函数定义/类定义/导入语句/调用表达式/类型标注）
3. **关系建立**：调用关系（call_expression）、继承（superclasses）、导入（import 语句）、类型引用
4. **存储**：按查询深度选择 SQLite 或 Neo4j，先建约束/索引再导入
5. **增量更新**：文件系统 watcher + content hash + 文件级原子替换
6. **暴露接口**：通过 MCP Server 向 AI Agent 暴露 search_symbols/get_callers/impact_analysis 等工具

### 向量检索的五类结构性盲区

「[Beyond Vector Similarity](https://arxiv.org/)」（2026）的系统实验确认，以下五类查询无论 embedding 质量如何提升都无法通过向量相似度解决：

1. **影响分析**：修改函数 X 会破坏什么？
2. **依赖链追踪**：函数 Y 间接依赖哪些接口？
3. **接口实现查找**：接口 Z 有哪些实现者？
4. **数据流追踪**：用户输入如何流向 SQL 查询？
5. **架构模式识别**：哪些模块形成循环依赖？

关键杠杆不是更强的 LLM，而是正确的图遍历算子——配备 9 个类型化遍历原语的 LLM Query Planner 达 F1=0.632，超越手写处理器的 0.472。

<Callout type="insight" title="混合检索已成标配">
  graph + vector 而非 graph vs vector。纯向量检索有结构性盲区（多跳推理），纯图检索缺乏自然语言语义理解，纯文本搜索无法处理概念查询。三信号融合（词法+语义+图）+ RRF/reranker 是当前收敛方向。[Gortex](https://github.com/gortex-ai/gortex) 用 BM25 + GloVe-50d + 图中心性重排 + RRF 融合，在 71K 节点图上 BM25 R@5=96.8%。
</Callout>

## 十、开放问题

1. **最优粒度**：符号级太细（上下文爆炸），文件级太粗（丢失语义），程序切片级可能是甜蜜点？Trace Gadgets 表明切片粒度优于完整函数图，但计算开销和实时性如何权衡？

2. **跨仓库/跨语言代码图**：当前最薄弱环节。微服务场景中调试时间比模块化单体多 35%（DZone 2024），但静态和动态图的融合方案尚不成熟。

3. **统一标准**：SCIP/Kythe/Glean 缺乏互操作性。MCP 在 Agent 接口层面提供了统一，但底层图模型和查询能力仍然碎片化。

4. **大上下文窗口的影响**：1M+ token 上下文窗口是否削弱代码图谱价值？更可能从必要条件变为效率杠杆——「有图可以做得更好更省」。

5. **嵌入式图数据库空白**：LadybugDB（Kuzu fork）能否接棒？如果失败，开发者工具场景将在 SQLite 表达力限制和 Neo4j 运维开销之间痛苦选择。

6. **全量重建 vs 增量更新的临界点**：随着 LLM token 成本持续下降，精心设计增量更新机制的投入是否还值得？

7. **形式化验证扩展性**：Goedel-Architect 在数学定理证明上取得突破，但从定理证明到通用软件验证的跨越程度尚不清楚。

8. **隐私控制**：CodeGraph/Gortex 将完整代码结构暴露给 AI Agent，企业场景需要细粒度访问控制和信息隔离机制。

### 选型建议

<Callout type="tip" title="选型指南">

**学习代码图谱原理** → 研究 [Joern](https://joern.io) 的 CPG 规范和 flatgraph 存储演进（Neo4j → OverflowDB → flatgraph），这是最好的教材。

**学习实用工程实现** → 研究 [Graphify](https://github.com/safishamsi/graphify) 的 Tree-sitter 集成方式和置信度标签设计；研究 [Gortex](https://github.com/zzet/gortex) 的三层语言架构和 Go 并发设计。

**安全分析生产使用** → 直接用 **Joern** 或 **CodeQL**，不要用新兴项目。

**AI Agent 代码上下文** → **Graphify** 当前最有深度，但项目太年轻。关注 **Gortex** 的后续发展。对高 star 项目保持警惕。

**评估任何新项目** → 先看 commits 数（反映真实工程量）和测试覆盖，不要看 star 数。用 [PhantomStars](https://github.com/tg12/phantomstars) 检查假星嫌疑。
</Callout>
